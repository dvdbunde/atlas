# M12-009 — Blazor Page Navigation and UX Improvements

## Objective

Improve the usability, consistency, navigation, and information presentation of the existing Citizen, Officer, and Admin Blazor pages through six focused UX refinements.

Preserve all existing business functionality, routes, workflows, permissions, and underlying behaviour. Build on the established M12 visual system and existing components.

## Context

M12-009 is a targeted follow-up to the M12 visual restyling work. The existing pages are functionally established, but several areas still have inconsistent navigation, weak information hierarchy, or unnecessary controls.

The agreed scope consists of six improvements:

1. Breadcrumb navigation and removal of redundant Back navigation.
2. Admin Users role-indicator refinement.
3. Admin Email Templates single-column refactor.
4. Operations Deeper Telemetry refactor and monitoring links.
5. Permit Designer Preview refactor.
6. Citizen Application Create/Edit UX improvements.

## Requirements

### 1. Breadcrumb navigation

- Review all Blazor pages in the Citizen, Officer, and Admin areas.
- Confirm that appropriate breadcrumbs exist from each relevant top-level dashboard through to the lowest-level page.
- Breadcrumbs must reflect the actual existing page hierarchy and routes.
- Use breadcrumbs as the canonical mechanism for parent/up navigation.
- Remove Back buttons or links whose only purpose is ordinary back/up navigation already represented by the breadcrumbs.
- Apply this consistently across Citizen, Officer, and Admin pages.
- Do not remove controls that perform another action.
- Preserve all routes, authorization, direct navigation, and page behaviour.

### 2. Admin Users role indicators

- Refine the role presentation for Admin, Officer, and Citizen on the Admin Users page.
- Preferred presentation: plain role text without a coloured background.
- If a visual treatment is retained, use distinct treatments for each role and keep them accessible and consistent with the M12 visual system.
- Remove the current overly dark shared role-indicator treatment.
- Do not change role names, role assignment, authorization, or user data.

### 3. Admin Email Templates

Refactor the existing two-column page into the approved single-column flow:

1. Fixed list of available templates.
2. Selected template content.
3. Available placeholders.
4. Template preview.
5. Existing Save, Preview, and Reset to default actions.

Preserve template selection, editing, placeholders, preview, save, and reset behaviour. The template set remains fixed: do not add template creation, deletion, activation, or other unsupported functionality.

### 4. Operations — Deeper Telemetry

- Refactor the existing Deeper Telemetry block.
- Provide a link to `https://portal.azure.com/` for Azure resources/information that can actually be checked there.
- Remove references to Azure Managed Grafana.
- Provide a link to the ATLAS Grafana Cloud dashboards:
  `https://atlasmonitoringdvb.grafana.net/dashboards`
- Supply the Grafana URL through the Blazor project's application configuration rather than hardcoding it in the Razor page.
- Follow the project's existing configuration/environment conventions.
- Treat the URL as non-secret configuration; add no credentials or tokens.
- Clearly distinguish Azure Portal and Grafana Cloud destinations.
- Preserve existing Operations health functionality and do not introduce a separate monitoring platform.

### 5. Permit Designer Preview

- Refactor the Preview tab so it resembles a realistic ATLAS application rather than a plain field/value dump.
- Reuse the existing application-detail presentation/components where practical.
- Generate clearly identified dummy/preview data based on the permit type currently being designed.
- Reflect the configured fields and document requirements where supported by the existing architecture.
- Preview data must be transient/in-memory and must never create, persist, submit, or otherwise modify a real application.
- Keep the preview clearly identifiable as a designer preview where necessary.
- Preserve the existing Permit Designer tabs and configuration workflow.

### 6. Citizen Application Create/Edit

- Remove the redundant `Continue Editing` button from the `Draft created successfully` notification.
- Remove the redundant `Continue Editing` button from the `Changes saved` notification.
- Treat successful save feedback as one current notification state rather than accumulating banners.
- After the initial draft creation, a subsequent successful save must replace the draft-created message with the current save result rather than leaving both visible.
- Restyle `Save Changes` and `Submit Application` using the established M12 button styling.
- Present these actions as a compact horizontal action group where width permits, while retaining sensible responsive behaviour on narrow screens.
- Preserve the distinction between saving and submitting.
- Clearly distinguish application data from supporting documents, using the application-detail presentation as the visual reference where appropriate.
- Preserve all existing fields, validation, document requirements, uploads, save behaviour, submit behaviour, and error/success handling.

- Do not introduce a new UI framework, component architecture, or frontend styling framework.
- Build on the existing M12 design tokens and shared styling.

- The M12 visual specification remains authoritative for colours, typography, spacing, surfaces, controls, responsiveness, and accessibility.
- The approved Email Templates and Citizen Create/Edit mockups are design references, not specifications for new functionality.

- The existing application-detail components should be reused rather than duplicated where technically sensible.
- Breadcrumb coverage must be checked comprehensively rather than only on the pages shown in the supplied screenshots.
- Consistency across Citizen, Officer, and Admin is preferred over isolated page-specific solutions.
