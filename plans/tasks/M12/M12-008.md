# M12-008 --- Admin Dashboard Refactor

## Objective

Refactor the existing ATLAS Admin Dashboard into a more informative and
useful administrative overview and navigation hub. Replace the current
six standalone counters with six clickable summary blocks that surface
meaningful system-state information while preserving the existing Admin
pages, routes, authorization, workflows, and underlying functionality.

## Context

The current Admin Dashboard provides separate counters for Permit Types,
Applications, Officers, Admins, Citizens, and Email Templates. The
presentation is clean after the M12 restyling work, but the dashboard
provides limited operational information and does not make the existing
Admin areas easy to reach.

M12-008 is an approved functional/information-design refactor of the
existing dashboard, not a wholesale UI redesign. It builds on the M12
visual foundation and shared styling established by M12-001 through
M12-007.

The dashboard should remain a concise overview rather than becoming a
general analytics or reporting page. The existing Admin pages remain the
source of detailed information.

## Requirements

- Implement only M12-008.
- Preserve the M12 visual language established by M12-001 through
    M12-007.
- Replace the current Admin Dashboard blocks with six summary blocks:
  - Permit Types
  - Applications
  - Users
  - Audit Logs
  - Email Templates
  - Operations
- Make each complete block clickable and navigate to its corresponding
    existing Admin page.
- Permit Types:
  - Include the total permit-type count in the block title,
        e.g. `Permit Types: 4`.
  - Show two body lines: Active and Inactive counts.
- Applications:
  - Include the total application count in the block title,
        e.g. `Applications: 4`.
  - Show counts for Draft, Submitted, Under Review, Info Requested,
        Resubmitted, Approved, and Rejected.
  - Do not render a status line when its count is zero.
  - Treat those seven statuses as the defined dashboard status set;
        do not invent additional statuses.
- Users:
  - Replace the separate Citizen, Officer, and Admin blocks with one
        Users block.
  - Include the total user count in the title, e.g. `Users: 3`.
  - Show body lines for Citizens, Officers, and Administrators.
- Audit Logs:
  - Add an informative recent-activity summary.
  - Prefer a last-24-hours audit-event count and latest-event
        recency where the existing data/services support those metrics.
  - Reuse existing audit-log/query infrastructure where practical.
  - Do not introduce broad audit analytics such as charts, rankings,
        or new reports.
- Email Templates:
  - Keep this as a simple total-count block because the existing
        Email Template functionality has no active/inactive distinction.
  - Do not invent an active/inactive metric or any other unsupported
        breakdown.
- Operations:
  - Add a lightweight system-health summary.
  - Prefer system health and last-checked information where
        supported by the existing Operations functionality.
  - Reuse the existing Operations health determination rather than
        creating a second dashboard-specific health calculation.
- Reuse existing services, queries, view models, and components where
    practical.
- Make the minimum targeted Razor/code changes necessary to support
    the approved dashboard information.
- Use existing ATLAS design tokens and shared component styling; avoid
    page-specific arbitrary styling.
- Preserve responsive behaviour and make the blocks usable at
    supported narrow/mobile widths.
- Preserve semantic navigation, keyboard accessibility, visible focus,
    and sufficient contrast.
- Do not add new pages, workflows, permissions, navigation
    destinations, or unrelated functionality.
- Do not rebuild shared components or introduce a new UI
    framework/component architecture.

## Notes

M12-008 follows M12-006 (Admin pages restyling) and should be
implemented after the Admin visual foundation is in place.

The intended dashboard information model is:

- `Permit Types: <total>` --- Active / Inactive
- `Applications: <total>` --- non-zero application-status counts
- `Users: <total>` --- Citizens / Officers / Administrators
- `Audit Logs` --- recent audit activity
- `Email Templates: <total>` --- total only
- `Operations` --- current system health / last checked

For Audit Logs and Operations, first inspect the existing implementation
and reuse the information already available. If a preferred metric is
not supported without disproportionate new backend work, use the most
useful existing metric that satisfies the purpose of the block and
document the deviation in the implementation summary rather than
inventing infrastructure.

The blocks should function as navigation surfaces to the existing
corresponding pages, not as new interactive workflows.
