# M12-009c --- Blazor UX, Filtering, Audit Display, and Application Detail Fixes

## Objective

Implement the eight approved M12-009c bug fixes and styling/layout
improvements across the Admin, Officer, and Citizen Blazor UI.

This is a focused follow-up to M12-009. Improve consistency, usability,
data presentation, and layout while preserving existing business
functionality, routes, permissions, workflows, and architecture.

## Context

M12 establishes a professional, restrained, consistent ATLAS visual
system while preserving existing pages, workflows, components, and
functionality. It explicitly prefers CSS-first changes and small
targeted markup adjustments rather than rebuilding pages or introducing
new UI architecture.

M12-009c contains the following live-review findings:

1. Admin Permit Types filter layout/styling.
2. Admin Application Explorer filter layout plus Last Updated semantics
    and draft timestamp behaviour.
3. Admin Users filter labels, search focus retention, and dropdown
    selection display.
4. Admin Email Templates bottom spacing.
5. Admin Audit Log list/detail user information and read-only Details
    presentation.
6. Officer Dashboard indicator spacing.
7. Citizen Dashboard filtering.
8. Citizen Application Detail applicant email.

The implementation must preserve existing business rules, routes,
permissions, workflows, and data semantics except where this task
explicitly corrects Last Updated behaviour and application date-filter
semantics.

## Requirements

### 1. Admin Permit Types --- filter section

Target: Admin Permit Types list.

- Replace the two `Active only` / `Inactive only` checkboxes with one
    status dropdown containing `All`, `Active`, and `Inactive`.
- Preserve the existing filtering semantics.
- Use the same labelled dropdown/filter styling conventions as other
    Admin list pages.
- Make the Search by Name input narrower/more proportionate.
- Make the Sort control wide enough for its selected values to be
    readable.
- Keep the filter row compact and balanced, with no excessive gaps.
- Preserve responsive usability.

Do not change permit-type filtering business logic beyond adapting the
UI from two equivalent checkbox filters to one status selection.

### 2. Admin Application Explorer --- filters and Last Updated

#### Filter layout

- Keep existing search functionality.
- Either give Search enough width or shorten its placeholder; prefer a
    concise, clear placeholder.
- Make Status slightly narrower.
- Make Sort wider enough for selected values to be readable.
- Make Date From and Date To more compact while remaining usable.
- Clearly indicate that the date range filters `Last Updated`,
    e.g. through a clear `Last Updated` label with From/To controls.
- Keep the complete filter row compact, aligned, and consistent with
    the other Admin list screens.

#### Date-filter semantics

- Inspect the actual query/service implementation.
- The date range must filter by the application's `Last Updated`
    value.
- If it currently filters by Submitted date or another field, correct
    it.
- Preserve existing search, status, permit-type, and sort behaviour.
- Apply From/To semantics consistently to Last Updated.

#### Draft Last Updated

Draft applications currently show no Last Updated value. Correct this.

- Initial draft creation/save must persist a Last Updated timestamp.
- Every subsequent successful draft save must update Last Updated.
- Drafts must have Last Updated before submission.
- The timestamp must follow the application's existing
    persistence/date-time conventions.
- Subsequent lifecycle changes must continue to maintain Last Updated
    according to existing rules.
- Admin Application Explorer must display the timestamp for drafts
    instead of `N/A`.
- Use the existing application/domain/persistence source of truth; do
    not create a page-specific timestamp.
- Trace entity, commands/handlers, persistence mapping, and queries as
    necessary.
- Add/update tests for initial draft creation and subsequent saves.
- Do not alter Submitted date semantics.

### 3. Admin Users --- filters, focus, and selection state

#### Filter labels/layout

Add visible labels to all three controls:

- Search
- Role
- Sort

Use the same labelled filter pattern and M12 styling as the other Admin
list screens. Keep the layout compact and aligned.

#### Search focus

The Search by name or email field currently loses focus after one
character because of re-rendering.

- Preserve the existing search behaviour.
- Keep the input focused after each search-triggering input/re-render.
- This must work for successive characters, deletion, and normal
    editing.
- Reuse the established ATLAS pattern for retaining search input focus
    through Blazor re-rendering, if one exists.
- Do not weaken search or introduce unnecessary new
    JavaScript/framework infrastructure.

#### Role and Sort selection

The Role and Sort dropdowns currently revert visually to their
first/default item after selection.

- The selected Role option must remain visibly selected.
- The selected Sort option must remain visibly selected.
- Selection must remain correct after filtering/sorting and subsequent
    renders.
- Defaults/reset behaviour must continue to work.
- Displayed selection and actual query/filter state must stay
    synchronized.
- Fix the underlying binding/state issue rather than applying a
    visual-only workaround.

### 4. Admin Email Templates --- bottom spacing

Add deliberate vertical space below the Save / Preview / Reset to
default buttons.

- Keep the current button order and functionality.
- Use the M12 spacing system.
- Do not alter the approved M12-009b edit/preview workflow.
- Do not alter the already-fixed notification placement or
    single-notification behaviour.
- This is a small layout-only correction.

### 5. Admin Audit Log --- user display and Audit Entry

Targets: Audit Log list and Audit Entry detail.

#### User identity

Replace raw `UserId` display with the user's `FirstName + LastName`.

The database contains Users fields including `Id`, `Email`, `FirstName`,
`LastName`, and AuditLogs contains `UserId`, `Action`, `EntityType`,
`EntityId`, `Details`, `Timestamp`, `IpAddress`, etc. The UserId
therefore remains the lookup key; it should not be the primary displayed
identity.

Apply this to:

- Audit Log list `User` column.
- Audit Entry `User` field.

Reuse existing user lookup/query infrastructure and avoid inefficient
N+1 access when the existing query layer can resolve the data
efficiently.

If a user cannot be resolved, handle it safely using existing
conventions; never invent user information.

#### Audit Entry email

Add the user's email on a separate line below/alongside the displayed
user name, using the existing user data source.

Conceptually:

- User: First Name Last Name
- Email: <user@example.com>

#### Remove IP Address presentation

Remove the `IP Address` row from Audit Entry.

Do not delete, migrate, or stop storing the underlying IP address. This
is presentation-only.

#### Details field

Keep Details as a non-editable, resizable multiline field.

Change its background to a light gray/neutral read-only treatment:

- lighter than the page background;
- clearly visually distinct;
- readable with sufficient contrast;
- not an excessively dark disabled appearance;
- still non-editable and resizable.

Prefer existing M12 surface/control tokens or established shared
styling.

### 6. Officer Dashboard --- indicator spacing

Target: Officer Dashboard / Applications Awaiting Review.

The indicators immediately above `Open Application` are too tightly
packed.

- Increase their spacing modestly.
- Preserve all indicators and their meanings.
- Preserve the Open Application button and workflow.
- Use existing Bootstrap/M12 spacing utilities where practical.
- Keep the group compact rather than redesigning the card.
- Check desktop and narrow/mobile presentation.

### 7. Citizen Dashboard --- add filters

Target: Citizen Dashboard / My Applications.

Add a compact labelled filter row above the applications list containing
three dropdowns:

1. `Permit Type`
2. `Status`
3. `Sort`

Requirements:

- Permit Type includes an all-permit-types option and applicable
    permit types.
- Status includes an all-statuses option and supported application
    statuses.
- Sort provides sensible existing application-list sort options,
    including the default/current ordering.
- Filtering/sorting applies only to the authenticated citizen's own
    applications.
- Reuse existing query/filter/sort mechanisms where practical.
- Visible labels and M12 list-filter styling are required.
- Keep the layout compact and responsive.
- Selected values must remain correctly displayed after
    filtering/re-rendering.
- Preserve existing application actions such as View Details and
    Continue Editing.
- Do not add Search, pagination, tabs, or other unrelated
    functionality.

### 8. Citizen Application Detail --- applicant email

Target: Citizen Application Detail.

The Citizen view shows the applicant name but not the email, while Admin
Application Detail correctly shows it.

- Inspect the shared `ApplicationDetails` / applicant presentation and
    data-loading path.
- Determine why the Citizen view does not populate the email.
- Make the Citizen Application Detail display the applicant email
    consistently with Admin.
- Prefer correcting the shared component/data flow where appropriate
    instead of duplicating presentation logic.
- Preserve existing authorization and privacy boundaries.
- The citizen must only see information already intended for their
    authorized application view.
- Preserve all other application-detail content and behaviour.

## Notes

M12-009c deliberately mixes presentation fixes with several
functional/data corrections. For each issue, identify the actual cause
before changing the UI.

For Application Explorer date filtering, verify the real query predicate
and date field; changing only the label is insufficient.

For draft Last Updated, trace the complete lifecycle from initial draft
creation through subsequent saves and persistence. It must be a real
persisted source of truth, not a calculated UI value.

For Users search focus, find and reuse the established ATLAS solution
for preserving focus through Blazor re-rendering.

For Users Role/Sort, fix the underlying binding/state mismatch so
displayed and applied values stay synchronized.

For Audit Log, reuse existing user lookup infrastructure and avoid
unnecessary N+1 calls where the query layer can project the required
name/email.

For Citizen Dashboard filters, ensure the authenticated-user restriction
is applied independently of user-selected filters.

For Citizen Application Detail, inspect both Citizen and Admin paths and
the shared application-detail component/data model before changing code.
Prefer a shared fix when safe.

The supplied screenshots are references for the reported issues, not a
specification for inventing unrelated UI.

The M12 plan requires existing cards, tables, forms, buttons, badges,
and page headers to be restyled rather than replaced; Bootstrap remains
the underlying framework; and validation must cover responsive
behaviour, keyboard focus, contrast, and preservation of existing
functionality.
