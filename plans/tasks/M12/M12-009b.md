# M12-009b — Email Templates and Permit Designer Preview UX Refinement

## Objective

Refine the two M12-009 areas that remained unsatisfactory during live visual validation:

1. **Admin Email Templates** — replace the current technically single-column but visually underdeveloped layout with the intended, wider single-column editing workspace represented by the approved M12-009 mockup.
2. **Admin Permit Designer Preview** — make the preview substantially more representative of a real ATLAS application-detail presentation, including a clearly separated Application Data section and more realistic field-type-specific sample data.

This is a focused follow-up to M12-009. The already-accepted M12-009 areas must remain functionally and visually unchanged unless a change is strictly necessary to support these two refinements.

## Context

M12-009 implemented six navigation and UX improvements across Citizen, Officer, and Admin pages. Live visual validation confirmed that the following areas are satisfactory and should not be revisited:

- Breadcrumb navigation and removal of redundant ancestor-navigation Back buttons/links.
- Admin Users role indicators as plain role text.
- Admin Operations monitoring links.
- Citizen Application Create/Edit save notifications and compact horizontal actions.

Two areas require further refinement.

### Email Templates

The current implementation has been converted from the previous two-column arrangement to a single-column sequence, but it is still visually close to the old interface stacked vertically. On desktop it is too narrow and leaves substantial unused horizontal space. The hierarchy, spacing, selector presentation, editing workspace, preview, and action area do not sufficiently reflect the approved M12-009 design mockup.

The intended workflow remains:

1. Fixed template list/selector.
2. Selected template details/content.
3. Available placeholders.
4. Editable template content.
5. Save / Preview / Reset to default actions.
6. Rendered preview.

Templates remain fixed system templates. Administrators must not gain template creation, deletion, or other CRUD capabilities.

### Permit Designer Preview

The current preview is functional and uses application-style presentation, but it still reads more like a rendered collection of configured fields than a convincing ATLAS application. In particular, **Application Data should be presented as its own clearly bounded section/card**.

The implementation should continue to use existing application-detail presentation patterns where appropriate rather than duplicating unrelated workflow UI or forcing `ApplicationDetailsLayout` to handle a designer preview that has no persisted application. The preview must remain transient/in-memory and must never create, save, or submit a real application.

## Requirements

### 1. Admin Email Templates — layout and visual refinement

#### 1.1 Use the approved mockup as the visual reference

Treat the approved M12-009 Email Templates mockup as the intended UX reference.

Do **not** interpret the requirement merely as "put the existing two columns one after another." The result must be a deliberate single-column admin editing workspace with clear hierarchy, appropriate width, spacing, and visual grouping.

The implementation should remain consistent with the established M12 visual language:

- Existing ATLAS shell and navigation.
- Existing M12 colors and design tokens.
- Existing typography and spacing conventions.
- Existing card, border, button, form-control, and focus treatments.
- Bootstrap remains the underlying UI framework.
- Do not introduce a new UI framework or component architecture.

#### 1.2 Desktop content width

The Email Templates page should make substantially better use of available desktop width.

- Replace the current narrow content constraint with a sensible wider content area.
- Target an effective desktop maximum width of approximately **1100–1200px**, subject to the existing application shell and responsive conventions.
- The template selector, template details/editor, placeholders, and preview should share a coherent content width/alignment.
- Do not make the page unnecessarily full-bleed; retain appropriate page margins and readable line lengths.
- The layout must remain usable at narrower desktop/tablet widths.

#### 1.3 Template selector

Retain the fixed list of available system templates, but present it as a proper selectable workspace section.

Each template option should:

- Be clearly identifiable by template name.
- Show the existing useful short description.
- Have a clear selected/unselected state.
- Provide a clear affordance that the row can be selected.
- Use the established ATLAS selected-state styling.
- Have appropriate row height, spacing, and typography.
- Avoid looking like a small legacy list control.

The selector must continue to represent the existing fixed templates only.

Do not add:

- Create template.
- Delete template.
- Duplicate template.
- Reorder template.
- Any other template CRUD or management functionality.

#### 1.4 Template details and editing workspace

Create a clearly defined **Template details** section/card.

- Show the selected template's name and description using the existing read-only behavior if they are not editable today.
- Make **Template content** the dominant editable element of this section.
- Give the template-content textarea substantially more vertical space than the current implementation so that realistic templates can be edited without excessive scrolling inside the control.
- Preserve the existing template editing behavior and placeholder syntax.
- Preserve existing validation and save behavior.
- Do not introduce a rich-text editor unless one already exists and is appropriate; plain template-content editing is sufficient.

The editing area should feel like the primary workspace of the page rather than a small form buried among several equally weighted cards.

#### 1.5 Available placeholders

Retain a dedicated **Available placeholders** section.

- Preserve all currently supported placeholders and their descriptions.
- Present them in a clean, readable structure consistent with the M12 table styling.
- Ensure the section is clearly associated with template editing.
- Do not invent or add placeholders.
- Do not change placeholder semantics or substitution behavior.

#### 1.6 Rendered preview

Retain a dedicated **Preview** section below the editing/placeholder content.

- Keep the existing rendered preview functionality.
- Make the preview use the available width appropriately.
- Present the rendered content in a visually distinct preview surface.
- Give the preview enough vertical space for realistic email content.
- Where practical using the existing implementation, make the presentation feel like an email preview rather than merely another generic grey text block.
- Do not introduce unnecessary email-client simulation or unrelated functionality.

The preview must continue to use the existing sample-data/rendering behavior.

#### 1.7 Action area

Provide one coherent action area for the template actions.

Retain the existing actions:

- **Save**
- **Preview**
- **Reset to default**

Use the established M12 button hierarchy:

- Save = primary.
- Preview = secondary.
- Reset to default = destructive/attention styling.

The actions should be:

- Horizontally aligned on normal desktop widths.
- Compact and consistent in height.
- Responsive/wrapping appropriately on narrow screens.
- Clearly associated with the template editing workflow.

Do not create a second, redundant action group unless there is a demonstrated existing functional requirement that cannot be satisfied by one coherent action area.

#### 1.8 Responsive behavior

The redesigned page must work at:

- Desktop width.
- Narrow desktop/tablet width.
- Mobile width.

On narrow/mobile layouts:

- Sections remain in a logical single-column sequence.
- Template rows remain easy to select.
- Textareas remain usable.
- Tables/content do not overflow the viewport unnecessarily.
- Actions may wrap when necessary but must remain accessible and visually coherent.
- No horizontal page-level overflow should be introduced.

### 2. Admin Permit Designer Preview — application presentation refinement

#### 2.1 Preserve the existing preview constraints

The preview must remain:

- Clearly identified as a **Designer preview**.
- Based on the current permit-type configuration.
- Generated from transient/in-memory data.
- Never persisted as a real application.
- Never submitted as a real application.
- Free of side effects against application persistence/workflow.

Do not introduce a new application-creation workflow.

#### 2.2 Application-style hierarchy

The preview should more convincingly resemble the presentation of a real ATLAS application.

Retain the existing:

- Permit type name.
- Permit type description.
- Preview notice.
- Preview application identifier/indicator where currently provided.

Use existing application-detail presentation patterns/components where practical and appropriate.

The objective is to demonstrate **what an applicant's configured application data and supporting-document requirements will look like**, not to simulate an entire persisted application lifecycle.

Do not fabricate:

- Reviews.
- Approval history.
- Activities.
- Real applicant records.
- Real application status transitions.
- Other workflow information that does not exist for the designer preview.

#### 2.3 Dedicated Application Data section

Create a clearly bounded **Application Data** section/card.

This is a required visual change.

The Application Data section should:

- Have a clear section heading.
- Be visually separated from the application header/summary.
- Present all configured permit fields.
- Present field labels and values with the same visual clarity and hierarchy used by the existing application-detail presentation.
- Handle the configured field types using sensible display formatting.
- Remain readable when many fields are configured.
- Avoid presenting the fields as an unstructured vertical dump.

Prefer reuse/refactoring of existing presentation patterns over creating a second, inconsistent application-detail visual language.

Do not require literal reuse of `ApplicationDetailsLayout` if its domain/context is inappropriate for a transient designer preview.

#### 2.4 Realistic dummy values

Improve preview sample values so they demonstrate the configured field types convincingly.

Use deterministic or otherwise stable sample values where practical. Examples:

- Short text → realistic sample text rather than a purely technical placeholder.
- Multiline text → a realistic short description containing one or two sentences.
- Number/currency → a plausible non-zero example such as `€25,000` where the field semantics support it.
- Date → a plausible formatted date.
- Boolean → `Yes` or `No`.
- Select/list → a valid configured option.
- Other existing supported field types → an appropriate display value based on the field's type.

Do not invent values that are inconsistent with the field configuration.

The preview should demonstrate the visual result of the field configuration rather than merely proving that a value can be rendered.

#### 2.5 Supporting Documents section

Keep **Supporting Documents** as a separate, clearly bounded section/card.

- Preserve the current behavior of deriving the preview from the configured document requirements.
- Clearly identify sample documents as examples rather than actual uploaded files.
- Maintain the distinction between application data and supporting documents.
- Do not persist or upload anything.

#### 2.6 Overall visual hierarchy

The resulting preview should follow a clear hierarchy similar to:

1. Designer preview notice.
2. Application/permit header and summary.
3. **Application Data** card/section.
4. **Supporting Documents** card/section.

Use the existing ATLAS application-detail visual language for these sections.

Avoid adding unrelated workflow controls, tabs, progress indicators, sticky actions, review panels, activity feeds, or other functionality that is not required by the designer preview.

### 3. Scope discipline

This task is a focused follow-up to M12-009.

Do not:

- Rework breadcrumbs.
- Rework Admin Users role indicators.
- Rework Operations.
- Rework Citizen Application Edit.
- Change application business logic unrelated to preview rendering.
- Add template CRUD.
- Add new template types.
- Add autosave.
- Add new workflow functionality.
- Introduce a new UI framework.
- Replace Bootstrap.
- Perform broad unrelated refactoring.

Small shared-component or CSS changes are acceptable only when they directly support the two required refinements and remain consistent with the existing architecture.

## Acceptance criteria

### 2 Email Templates

1. **Single-column workspace**
   - The page remains a single-column workflow.
   - The result is a deliberate redesign rather than the old two-column UI simply stacked vertically.
   - Template selector, details/editor, placeholders, and preview form a coherent vertical workspace.

2. **Desktop width**
   - At a normal desktop viewport, the page uses a substantially wider content area consistent with approximately 1100–1200px maximum width, subject to existing shell conventions.
   - The current narrow presentation and excessive unused horizontal space are resolved.

3. **Template selector**
   - The fixed template list is clearly selectable.
   - Each row shows template name and useful description.
   - Selected state is visually obvious and consistent with M12.
   - No template CRUD functionality is added.

4. **Template details/editor**
   - Template details are clearly separated from the selector.
   - Template content is the dominant editing control.
   - The content textarea has sufficient height for realistic template editing.
   - Existing editing, validation, and save behavior is preserved.

5. **Placeholders**
   - Available placeholders remain clearly presented with their existing descriptions.
   - Placeholder behavior is unchanged.

6. **Preview**
   - Rendered preview remains available.
   - Preview is a clearly distinct section and makes appropriate use of the wider content area.
   - Existing preview behavior remains functional.

7. **Actions**
   - Save, Preview, and Reset to default remain available.
   - They are presented as one coherent action group.
   - Save is primary, Preview secondary, Reset to default attention/destructive.
   - Actions are compact, horizontally aligned on desktop, and responsive on narrow screens.

8. **Responsive behavior**
   - The page remains usable without page-level horizontal overflow on narrow/mobile viewports.
   - Template selection, editing, preview, and actions remain accessible.

### 2 Permit Designer Preview

1. **Preview safety**
   - The preview remains clearly identified as a designer preview.
   - No real application is created, persisted, uploaded, or submitted.

2. **Application-style presentation**
    - The preview clearly resembles the presentation of a real ATLAS application rather than a raw field dump.
    - Existing application-detail presentation patterns are reused/refactored where appropriate.

3. **Dedicated Application Data section**
    - Application Data is presented in its own clearly bounded visual section/card.
    - All configured fields are included.
    - Labels and values are clearly distinguishable.
    - The section is visually coherent and consistent with application-detail presentation.

4. **Realistic sample data**
    - Sample values are sensible for the configured field types.
    - Numeric/currency, dates, booleans, selections, text, and multiline values are displayed in an appropriate manner.
    - Values are demonstrative and do not imply real applicant data.

5. **Supporting Documents**
    - Supporting Documents remains a distinct section/card.
    - Configured document requirements are represented.
    - Sample documents are clearly examples and are not persisted.

6. **Overall hierarchy**
    - The visual order and hierarchy are clear:
      Designer preview notice → application header/summary → Application Data → Supporting Documents.
    - No unrelated workflow functionality is introduced.

7. **Regression safety**
    - Existing Email Templates behavior continues to work.
    - Existing Permit Type Designer configuration functionality continues to work.
    - Existing routes, authorization, and business behavior remain unchanged.

8. **M12-009 regression**
    - The four already-accepted M12-009 areas remain unaffected:
      - Breadcrumb navigation.
      - Admin Users role indicators.
      - Operations monitoring links.
      - Citizen Application Create/Edit save notifications/actions.

9. **Code quality**
    - Implementation follows existing ATLAS architecture and frontend conventions.
    - No unnecessary duplication or broad refactoring is introduced.
    - Existing shared components/styles are reused where appropriate.

## Notes

### Approved Email Templates design direction

The approved design reference establishes the intended information architecture:

1. Page heading and description.
2. Templates selector with meaningful selectable rows.
3. Template details/content editing area.
4. Available placeholders.
5. Rendered preview.

It should therefore demonstrate the resulting application presentation convincingly while remaining a safe, transient designer preview.

Do not simulate workflow/history that is not part of the preview data.
