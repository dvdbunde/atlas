# M12-010 — General Blazor Screen Cleanup

## Objective

Perform a focused cleanup pass across the existing ATLAS Blazor screens to standardize date/time presentation, remove redundant application information, correct Admin Application Explorer sorting/filter layout, and improve small spacing issues identified during rendered UI review.

Preserve existing functionality, workflows, information architecture, underlying data, and the established M12 visual system. Treat this as targeted cleanup rather than redesign.

## Context

M12 established a professional, restrained, consistent visual language across Citizen, Officer, and Admin areas while preserving existing pages, components, workflows, and functionality. M12-010 continues that approach as a general Blazor cleanup pass.

The five cleanup areas below were identified during visual review. The supplied screenshots are examples, not an exhaustive inventory. The developer must inspect the complete relevant Blazor application, especially for date formatting.

The M12 plan requires CSS-first implementation, small targeted markup changes, reuse of existing components, Bootstrap retention, and validation of functionality, responsiveness, keyboard focus, and accessibility.

## Requirements

### 1. Standardize date/time formatting across Blazor

Perform a full audit of all Blazor screens for user-visible date/time formatting.

Where a timestamp is displayed, standardize the presentation to:

**`dd/mm/yyyy hh:mm`**

Check all relevant:

- List screens
- Detail screens
- Dashboards
- Activity/timeline/history displays
- Document/upload timestamps
- Other user-visible date/time fields

Use the existing Admin Application Explorer presentation as the reference.

For the Admin Application Explorer `Last Updated From` and `Last Updated To` filters, use the date-only format:

**`dd/mm/yyyy`**

These filters must remain date-only and must not be changed to include a time component.

Do not alter underlying date/time values, timezone semantics, or business logic. This is a presentation/input-format consistency change.

### 2. Remove redundant Submitted Date displays

Remove Submitted Date from:

- Citizen Dashboard / My Applications application-list columns.
- Admin Application Explorer application-list columns.
- Citizen application-detail header.
- Citizen application-detail Application Summary.
- Officer application-detail header.
- Officer application-detail Application Summary.
- Admin application-detail header.
- Admin application-detail Application Summary.

The Submitted event/date in the **Activity** block on application detail screens must remain.

This is UI cleanup only. Do not remove or alter the underlying `SubmittedDate` domain property, persistence, query data, or functionality.

Where application-detail screens share components, make the change at the appropriate shared level where practical and verify all three roles.

### 3. Remove redundant Officer Notes block

Remove the **Officer Notes** block from all application detail screens:

- Citizen
- Officer
- Admin

The block duplicates information already represented by the structured **Review History** and exposes it as unformatted/raw text.

Requirements:

- Remove the Officer Notes UI presentation.
- Keep Review History intact and functional.
- Do not delete, migrate, or otherwise alter underlying stored notes/audit data.
- Use the appropriate shared application-detail component where practical.

### 4. Correct Admin Application Explorer default sort and filter layout

On Admin → Applications / Application Explorer:

#### Default sorting

- Change the default sort from **Submitted** to **Updated**.
- The initial list must therefore be ordered by **Last Updated**.
- Preserve all existing explicit sort options and behavior.

#### Filter sizing

Rebalance the filter row:

- Make **Sort** wider.
- Make **Status** slightly narrower.
- Make **Last Updated From** slightly narrower.
- Make **Last Updated To** slightly narrower.
- Use the recovered horizontal space to give Sort a more appropriate width and improve overall proportionality.

Preserve responsive behavior, filtering functionality, selected values, and accessibility.

### 5. Add bottom spacing below Citizen Application Edit actions

On the Citizen Application Edit screen:

- Add appropriate bottom spacing/padding beneath **Save Changes** and **Submit Application**.
- Keep the buttons, order, styling, and workflow unchanged.
- Prevent the action group from sitting directly against the bottom edge of the content/page.
- Verify the spacing at supported viewport sizes.

## Constraints

- Preserve the established M12 visual system and M12 plan.
- Treat this as cleanup and targeted UX refinement, not a redesign.
- Prefer CSS-first changes and small targeted markup changes.
- Keep Bootstrap as the underlying CSS/layout framework.
- Reuse existing shared components and styling patterns where practical.
- Do not introduce a new UI framework, component architecture, or styling framework.
- Do not invent functionality or change information architecture.
- Do not remove underlying domain data merely because its presentation is removed.
- Do not change authentication, authorization, persistence, or business rules except for the narrowly required existing Admin sort behavior.
- Preserve underlying date/time values and timezone/business semantics.
- Preserve the `ModifiedDate` / Last Updated semantics established by M12-009c; do not introduce a separate `LastUpdated` domain property.
- Avoid unrelated refactoring or opportunistic cleanup outside these five requirements.
- Follow all existing `.github` instructions and agents, including design-first/test-first development, testing, accessibility/security, and PR/review workflow.
