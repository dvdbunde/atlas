# M12-011 — Officer Self-Unassignment

## Objective

Allow an officer to remove their own assignment from an application from the application detail screen.

When an application is assigned to the currently authenticated officer and is in `Under Review`, the officer must be able to relinquish the assignment. The application must then return to `Submitted` with no assigned officer.

This is a new workflow and must not alter or regress existing application assignment, review, or decision flows.

## Context

ATLAS currently supports assigning an application to an officer for review. An application in `Under Review` has an assigned officer and assignment data persisted on the application.

A new workflow is required so that the currently assigned officer can explicitly release an application back to the unassigned queue.

The resulting state must be:

- Status: `Submitted`
- Assigned Officer: none
- `AssignedOfficerId`: cleared/null
- `AssignedDate`: cleared/null

After release, another officer must be able to assign the application to themselves through the existing assignment flow.

The new action must be available only from the application detail screen.

## Requirements

### 1. Officer self-unassignment action

Add a new action on the officer application detail screen allowing the currently assigned officer to remove their own assignment.

The action must be available only when all of the following are true:

- the authenticated user is an officer;
- the application is assigned to that officer;
- the application status is `Under Review`.

Do not expose the action on officer dashboards, queues, lists, or other screens.

### 2. Self-unassignment workflow

Executing the action must atomically:

1. verify that the authenticated officer is the currently assigned officer;
2. verify that the application is in `Under Review`;
3. clear the assigned officer;
4. clear the assignment date;
5. change the application status from `Under Review` to `Submitted`;
6. persist the state change.

The operation must fail safely if the preconditions are no longer true.

Do not allow an officer to remove another officer's assignment.

### 3. Reassignment

After successful self-unassignment, the application must be eligible for the existing officer assignment flow.

Another officer must be able to assign the now-`Submitted` application to themselves using the existing workflow.

Do not modify the existing assignment behavior beyond what is necessary to support the new released state.

### 4. Authorization and concurrency

Enforce the self-unassignment rule server-side/domain-side; UI visibility alone is insufficient.

The operation must validate the current assignment and status at execution time so that a stale page cannot be used to release an application that has already changed state.

Handle concurrent changes safely according to existing ATLAS concurrency and transaction conventions.

### 5. Auditability

The state-changing operation must be audited according to the existing ATLAS auditing conventions.

The audit information should clearly identify that the officer released their own assignment and that the application returned to `Submitted`.

Do not remove or alter historical audit data.

### 6. User interface

Place the new action only on the officer application detail screen.

Use the existing ATLAS button/action styling and workflow conventions.

The action should be visually distinguishable from decision actions such as Approve, Reject, and Request Information, because self-unassignment is a workflow/assignment action rather than a decision.

Provide appropriate confirmation and success/error feedback consistent with existing application workflows if the established UI patterns support it.

Do not introduce a new UI component framework.

### 7. Persistence

On successful self-unassignment:

- `AssignedOfficerId` must be null/cleared.
- `AssignedDate` must be null/cleared.
- application status must be `Submitted`.

Do not introduce duplicate assignment fields or alternative state properties.

### 8. Existing flows

Existing flows must continue to behave exactly as before, including:

- officer assignment;
- opening an assigned application;
- Approve;
- Reject;
- Request Information;
- document operations;
- existing citizen workflows;
- existing administrator workflows;
- reassignment of a submitted/unassigned application.

Do not change the semantics of `Entity.ModifiedDate` or introduce a separate last-updated field.
